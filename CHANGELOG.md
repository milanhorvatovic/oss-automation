## [Unreleased]

### Added

- `dependabot-policy` reusable workflow: a tiered Dependabot auto-merge policy — eligible patch/minor updates are approved and armed, majors and privileged dependencies are armed but held for a maintainer, veto labels are a hard stop with reactive disarm. Callers run on `pull_request_target`, so the delegation carrying the App credentials and the guards around it are read from the default branch rather than from the pull request, and the App's private key lives in the Actions secret store alone, its client id alongside it as a repository variable; a caller delegates only for pull requests targeting the default branch, since that is the tree a `pull_request_target` run executes.
- `dependabot-reconciler` reusable workflow: a scheduled sweep re-driving approved or armed Dependabot PRs after dropped events or base-branch advances, leaving everything else for manual triage.
- `oss-automation-guards` pytest test-pack: structural guards for job timeouts, full-commit-SHA action pins whose trailing comment is the pinned version — a comment that merely contains a digit, such as a branch and a date, does not satisfy it — pinned default-token scopes, and the trust-model binding of credentialed PR-triggered workflows.
- A coverage floor of 90% across both suites combined, measured by import name so it reads the installed package CI actually runs.
- `verify` reusable workflow holding the lint-and-both-suites definition that `test.yaml` and `release.yaml` had each carried a copy of, so a tag cannot be published by a weaker check than a pull request faced. Its status contexts are `verify / test (3.10)` and `verify / test (3.14)`.
- `.github/release.yml`, grouping GitHub's generated notes into categories a consumer reads in priority order. `release-prepare.yaml` writes those notes into the changelog section and `release-tag.yaml` publishes it, so the file shapes both halves of every release.
- Two further structural guards in `oss-automation-guards`: a credentialed job on a pull-request trigger never checks out, and a `run:` script never interpolates a `${{ … }}` expression into the shell it is about to execute. Both were invariants this repository's workflows already held and its comments already claimed; neither was enforced.
- `scorecard` workflow running OpenSSF Scorecard weekly and on pushes to the default branch, uploading its SARIF to code scanning and publishing the score so a consumer can check it before calling anything here. `ossf/scorecard-action` and `github/codeql-action` join the privileged-dependency list, since both execute under a write scope.
- Distribution metadata on the guard package — project URLs, classifiers, keywords, and a `py.typed` marker, so an installed copy carries its own provenance and its annotations reach a consumer's type checker.
- Community health files: a Contributor Covenant 2.1 `CODE_OF_CONDUCT.md`, issue forms that route security reports to a private advisory before an issue can be opened, and `AGENTS.md` for the failure modes an agent contributor hits that a human reading CONTRIBUTING.md does not.
- `docs/consumers.md`, the setup a caller needs that no `uses:` line can carry: the automation App and its permissions, the secret store the credentials belong in, the fixed kill-switch variable and veto labels, the repository settings and ruleset that decide whether an armed pull request ever merges, and copy-paste callers for both Dependabot workflows.
- A closing annotation on every `dependabot-policy` run naming the tier it derived, the veto and authorship states behind it, and whether auto-merge was armed and the update approved. The tier had only ever been a step output, so a held update left a maintainer inferring which gate held it from which steps ran. An event whose payload already carries a veto label skips the policy job entirely, so the disarm job annotates that hold instead; a label added later is reported by the run's own live check.
- Reusable release workflows in two flavors — `release-tag` (tag-driven: tag/changelog parity by default, tag/manifest parity once the caller passes a `version-command`, and curated-plus-generated notes) and `release-please` (Conventional-Commits driven) — with this repository releasing via the tag-driven flavor behind its full suite.
- A `draft` input and a `release-id` output on `release-tag`, for a caller that attaches assets. `release.published` carries whatever is attached when it fires and no second event follows an upload, so a release published before its assets announces an empty one — permanently — to everything that reads it: the API, the releases page, a webhook a mirror is watching. A drafting caller uploads first and publishes last, so what they all see is the finished release. The default is unchanged, so a caller that attaches nothing needs no edit. Note that publishing with `GITHUB_TOKEN` starts no `on: release` workflow run either way, which is a property of the token rather than of the ordering; a caller that needs those runs publishes with an App or PAT, and `docs/consumers.md` says so.
- A composite action at `guards/`, so the guards can be run as `uses: milanhorvatovic/oss-automation/guards@<sha>` rather than three steps of setup, install and invocation. The sub-action is named rather than sitting at the root because this repository publishes several things and the root says which of them you meant only by accident; addressing it fails with a message pointing at the sub-action instead. It installs the test-pack from the pinned revision — its dependencies still resolve from an index — into a virtual environment of its own, so the install leaves the caller's Python as it found it. Asking for `python-version` is the exception: `setup-python` puts that interpreter on the job's PATH and later steps see it. The reusable workflows keep their `.github/workflows/…` paths, which is where GitHub resolves a reusable workflow from and also the only shape that can hold their guarantees — an action runs inside the caller's job under the caller's token, and could not keep a credentialed job checkout-free or a publishing job free of the code that built the artifact. `test.yaml` runs the action against this repository's own tree on every pull request.
- Release assets, and a provenance attestation over them: a tag now publishes the built wheel and sdist, a CycloneDX SBOM naming that wheel as its root component and the closure it resolved to at release time, and `SHA256SUMS`, with `actions/attest-build-provenance` binding every one of them to the workflow run and commit that produced them, so `gh attestation verify` answers for a download what a pin answers for a `uses:` reference — checksums and an SBOM included, since a metadata file that cannot establish its own origin is one an attacker with write access could rewrite under a still-valid attestation. The build runs in a job holding no credentials and hands its output to the credentialed one, so the backend, the SBOM generator and whatever they resolve to never share a runner with a token that can write — and it builds with `--no-isolation` against `requirements-release.txt`, a hash-locked closure of the build backend and the SBOM generator. Pinning the frontend pins nothing about the backend, an extra cannot pin a transitive, and `pip install .` would resolve a backend of its own before either — so the tooling that produces the bytes a release attests is now fixed by hash rather than by whatever resolves on the day. The assets are attached before the release is announced, per the `draft` entry above, and the ordering puts the recoverable half last: a release cannot be created twice, while an upload is a re-runnable `--clobber` and publishing is a PATCH.
- A type check over the guard package in `verify.yaml`. The wheel has always shipped `py.typed` and a `Typing :: Typed` classifier, which is a promise to every consumer's type checker that nothing here was making good on.
- `.python-version`, `.gitattributes` and `.editorconfig`, and an sdist file list in `pyproject.toml` — without which hatchling mirrors the working tree, and a file ignored only by a per-clone `.git/info/exclude` travels into a published artifact. `verify` builds an sdist and runs the suite it ships, so the list cannot quietly stop covering what the tests read.
- `.github/PULL_REQUEST_TEMPLATE.md`, prefilling the description shape CONTRIBUTING.md specifies and carrying a before-merge checklist whose first item is the label. A label decides which category a pull request lands in, and so what the changelog says about it, and the convention had lived only in CONTRIBUTING.md — where it was already missed once. The rest of the checklist is the failure modes AGENTS.md names.
